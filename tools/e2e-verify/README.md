# 端到端验证脚本

一条命令跑完 49 项断言，覆盖从登录到采购入库闭环的完整链路。

## 用法

```bash
# 1. 先启动后端（需要数据库已建好）
cd erp-server && mvn clean package -DskipTests
java -jar erp-admin/target/erp-server.jar

# 2. 另开一个窗口跑验证
cd tools/e2e-verify
python -I e2e_verify.py
```

Python 3.8+，不需要任何第三方库。用退出码表示结果（0 = 全部通过，1 = 有失败项），可直接挂 CI。

## 覆盖范围

| 分组 | 验证内容 |
|---|---|
| 1. 基础与鉴权 | 健康检查；不带 Token 返回 401；admin 登录拿 Token；错误密码被拒；getInfo 的角色与权限；超级管理员的 `*:*:*`；动态路由返回 4 个一级菜单且组件正确；字典接口可用 |
| 2. 主数据 | 物料/仓库/供应商新增；重复编码被拒且提示可读；列表可查；**id 序列化为字符串**（防 JS 精度丢失） |
| 3. 库存闭环 | 新建入库单（单头+明细）；审核前台账为空；审核；**重复审核被拒**；台账数量正确；写入流水且变动前/后数量正确、能追溯来源单据、带出跨模块取到的物料名；**库存不足时出库被拒**；失败后库存未被改动（事务回滚） |
| 4. 采购闭环 | 新建订单；**总金额由后端按明细汇总**；审核；待收货列表；新建收货单；**重复确认被拒**；回写入库单号；库存 = 手工入库 + 采购收货；入库单可追溯到收货单；订单状态流转为已完成；流水条数正确 |
| 5. 权限隔离 | 创建采购员并分配角色；采购员登录；**只能看到 2 个菜单**；调系统管理接口返回 **HTTP 403**；有权限的接口正常访问 |

## 设计要点

**脚本可重复运行。** 每次运行用时间戳生成唯一的物料/仓库/供应商编码和用户名
（`E2E-M191130` 这种），所以不会撞唯一索引，也不需要在两次运行之间清理数据库。

第一版没做这件事，第二次运行时就因为"编码已存在"整片失败——**验证脚本本身必须可重复执行**，
否则它只能在干净的库上跑，价值大打折扣。

**断言要能表达"累积数据"。** 例如"采购收货自动生成了入库单"，
早期写成断言「这类入库单恰好 1 张」，第二次运行后数据库里有 2 张就失败了。
正确的断言是「**这张**收货单生成的那张入库单存在且单号可追溯」——
断言的对象应该是本次运行产生的数据，而不是全局计数。

**数值比较用 Decimal，不要比字符串。** 后端序列化 `BigDecimal` 可能是 `0` 也可能是 `0.0`，
字符串比较会误判。

## 它验不了什么

- **浏览器里的真实交互**：路由跳转、表单校验、组件渲染、`v-hasPermi` 指令是否真的隐藏了按钮。
  这些必须人打开 http://localhost:3000 点一遍。
- **并发**：脚本是串行的，"重复审核被拒"验的是状态判断，不是真正的并发竞争。
  真正的并发需要用 ab / JMeter 同时打同一个审核接口，再检查库存有没有被加两次。
- **跨页面的视觉效果**：表格列是否对齐、字典标签颜色对不对之类。

## 什么时候跑它

- 改动了后端接口、DTO 字段、权限串之后
- 升级依赖之后（尤其是 Spring Boot / MyBatis-Plus）
- 合并别人代码之后
- 提交前（可作为自检）

它比人点页面快得多，而且能发现人眼容易忽略的问题 ——
本项目开发中就靠这类验证发现了「登录查用户时漏查 password 字段」这种
只有真跑起来才暴露的错误（SQL 少一个列名，编译器完全没有意见）。
