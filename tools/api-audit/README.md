# 前后端接口对账脚本

## 为什么需要它

前后端分头开发时，接口对不上有两种情况，危害完全不同：

| 类型 | 表现 | 发现难度 |
|---|---|---|
| **路由对不上** | 404 / 405，控制台有报错 | 容易，一点就发现 |
| **字段名对不上** | 接口返回 200，页面正常打开，**只是数据不对** | 很难，容易被当成"数据本来就这样" |

第二种是真正危险的。本项目开发过程中就实际出现过：

- 前端传 `bizDateStart`，后端 DTO 里叫 `bizDateBegin` → 起始日期筛选完全不生效，零报错
- 前端传 `materialCode`，后端查询对象里没有这个字段 → 物资编码筛选被忽略，用户看到的是全部数据

这两个问题靠人工核对很容易漏（几十个字段），靠点页面也很难发现（要恰好注意到"筛了跟没筛一样"）。
所以写成脚本，随手就能跑。

## 用法

```bash
# 1. 启动后端。不需要数据库也能跑（接口注册信息与数据无关）：
#    加这两个参数即可让应用在没有库的情况下起来：
#      --spring.datasource.hikari.initialization-fail-timeout=-1 --spring.flyway.enabled=false
#    详见根目录 README 的「不连数据库的冒烟启动」一节。

# 2. 跑对账（Python 3.8+，无需第三方库）
cd tools/api-audit
python -I ApiAudit.py   E:/AI-Cladue/AI_MyErp/erp-web/src http://localhost:8080
python -I FieldAudit.py E:/AI-Cladue/AI_MyErp/erp-web/src http://localhost:8080
```

两个脚本都用**退出码**表示结果（0 = 通过，1 = 有问题），可以直接挂到 CI 上。

## 两个脚本分别在查什么

### ApiAudit.py —— 路由级

后端路由**不靠 grep 注解**，而是从运行中的应用的 OpenAPI 文档里取（`/v3/api-docs/{group}`）。
这是唯一权威来源：它已经正确处理了类级 `@RequestMapping` 前缀、路径拼接、路径变量。
grep 注解字符串的做法不可靠 —— 注解可能拼错、前缀可能漏算。

前端则解析 `api/*.js` 里的 `const BASE = '...'` 常量，把模板字符串展开成实际路径
（`${BASE}/list` → `/mdm/material/list`）。

比对的是 `(HTTP方法, 路径)` 二元组。只比路径会漏掉"路径对但方法错"，那同样是 405。

### FieldAudit.py —— 字段级

把后端所有 schema 的属性名收成一个集合，再检查前端的 `queryParams.X` 与表格 `prop="X"`
有没有不在集合里的。

**这是筛查，不是证明。** 它用的是"全体字段的并集"而不是"精确到某个接口的字段"，
所以会有假阳性（某个字段在别的模块合法、但在当前页面是错的）。反过来假阴性很少，
适合当守门员；命中后需要人工确认是哪一边写错了。

要彻底消除假阳性，得把每个页面映射到它实际调用的那个 DTO —— 成本高得多，
接口稳定下来之后再做更划算。

## 维护提示

- 新增业务模块后，把模块名加进脚本里的 `GROUPS` 列表（同时要在 `OpenApiConfig` 里加对应的
  `GroupedOpenApi` Bean，否则 OpenAPI 文档里没有这个分组）
- 前端 `api/*.js` 如果换了新的写法（比如改用 axios 实例直接调、或 url 用变量拼接得更复杂），
  解析正则要同步更新，否则会静默漏掉一些调用 —— 这类"脚本自己失效"比接口失效更隐蔽，
  改完记得先看输出里的计数是否符合预期
