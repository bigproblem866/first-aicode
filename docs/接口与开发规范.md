# 接口与开发规范

> 本文是**开发时必须遵守的契约**。新增业务模块前请先读完「新增一个 CRUD 模块的 SOP」一节。
> 代码里的约定以本文为准；本文与代码不一致时，说明有一处该改。

---

## 一、路径与权限命名

### 1. 接口路径

```
/api/{模块}/{资源}/{动作}
```

模块名使用**与权限串完全相同的缩写**，不允许一个模块两种叫法：

| 模块 | 路径前缀 | 对应 Maven 模块 | 权限串前缀 |
|------|----------|----------------|-----------|
| 系统管理 | `/api/system` | erp-system | `system:` |
| 主数据 | `/api/mdm` | erp-mdm | `mdm:` |
| 库存管理 | `/api/inv` | erp-inventory | `inv:` |
| 采购管理 | `/api/pur` | erp-purchase | `pur:` |

Controller 上直接写全路径（含 `/api`），**前端 Vite 代理不做任何 rewrite**。
这样浏览器、curl、Swagger 里看到的是同一个地址，不会出现"文档里写 /api/xxx，实际要调 /xxx"的歧义。

### 2. 权限串

```
模块:资源:动作
```

动作固定为：`list`（列表）、`query`（详情）、`add`、`edit`、`remove`、`audit`（审核类单据）、`confirm`（确认类操作）、`export`。

**权限串必须与菜单种子数据（`R__seed_system_menu.sql` 的 `perms` 列）逐字一致**。
写错一个字母的现象是「按钮能看见，点下去 403」，排查时很难联想到是拼写问题。

## 二、统一返回格式

### 成功

```json
{ "code": 200, "msg": "操作成功", "data": { } }
```

### 分页

```json
{ "code": 200, "msg": "操作成功", "data": { "total": 42, "rows": [ ] } }
```

前端分页组件固定取 `data.total` / `data.rows`。

### 失败

```json
{ "code": 500, "msg": "物料编码已存在：M001" }
```

### HTTP 状态码约定（重要）

| 场景 | HTTP 状态 | body.code |
|------|-----------|-----------|
| 成功 | 200 | 200 |
| 业务失败（编码重复、状态不允许等） | **200** | 400 / 500 |
| 参数校验失败 | **200** | 400 |
| 未登录 / Token 过期 | **401** | 401 |
| 已登录但无权限 | **403** | 403 |
| 系统异常 | **200** | 500 |

为什么业务失败用 HTTP 200：HTTP 层面这次请求是成功送达并处理了的，失败发生在业务语义层，
前端统一按 `res.code !== 200` 弹提示即可。
而 401/403 必须用真实状态码 —— 前端要区分「登录过期（清 Token 跳登录页）」和
「无权限（只弹提示，绝不能把人踢下线）」，两者的处理逻辑不同。

## 三、分页入参

所有列表接口统一接收：

| 参数 | 说明 |
|------|------|
| `pageNum` | 页码，从 1 开始，默认 1 |
| `pageSize` | 每页条数，默认 10，**服务端硬上限 500** |
| `orderByColumn` | 排序字段，传驼峰值（如 `materialCode`），服务端转下划线并做白名单校验 |
| `isAsc` | `asc` / `desc` |

业务查询条件 DTO 继承 `com.erp.common.core.domain.PageQuery` 即可自动获得上述参数。

## 四、接口清单

### 4.1 认证 `/api/auth`

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| POST | `/api/auth/login` | 免登录 | 入参 `{username, password}`，返回 `{token}` |
| POST | `/api/auth/logout` | 需登录 | 删除服务端登录态 |
| GET | `/api/auth/getInfo` | 需登录 | 返回 `{user, roles, permissions}` |
| GET | `/api/auth/routers` | 需登录 | 返回动态路由数组 |

### 4.2 系统管理 `/api/system`

资源：`user`、`role`、`menu`、`dept`、`dict/type`、`dict/data`

标准 CRUD 端点（以 user 为例）：

| 方法 | 路径 | 权限 |
|------|------|------|
| GET | `/api/system/user/list` | `system:user:list` |
| GET | `/api/system/user/{id}` | `system:user:query` |
| POST | `/api/system/user` | `system:user:add` |
| PUT | `/api/system/user` | `system:user:edit` |
| DELETE | `/api/system/user/{ids}` | `system:user:remove` |

专用端点：

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| PUT | `/api/system/user/resetPwd` | `system:user:resetPwd` | 重置他人密码 |
| GET | `/api/system/role/optionselect` | — | 角色下拉（给用户分配角色用） |
| GET | `/api/system/menu/treeselect` | — | 菜单树下拉（给角色分配权限用） |
| GET | `/api/system/menu/roleMenuTreeselect/{roleId}` | — | 菜单树 + 该角色已选中项 |
| GET | `/api/system/dept/treeselect` | — | 部门树下拉 |
| GET | `/api/system/dict/data/type/{dictType}` | — | **按类型取字典**，前端 `DictSelect` 组件调它 |

> `dict/data/type/{dictType}` 必须免权限校验（只加 `@PreAuthorize("isAuthenticated()")`）：
> 任何页面都可能用它渲染状态列，如果要求 `system:dict:list` 权限，
> 会出现「有单据权限的人看不到状态文字」。

### 4.3 主数据 `/api/mdm`

资源：`material`（**模板资源，写全套**）、`materialCategory`、`customer`、`supplier`、`warehouse`

标准 CRUD 端点同上。额外：

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/mdm/material/optionselect` | 需登录 | 物料下拉（单据选料用），返回精简字段 |
| GET | `/api/mdm/materialCategory/treeselect` | 需登录 | 物料分类树下拉 |

### 4.4 库存管理 `/api/inv`

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/inv/stock/list` | `inv:stock:list` | 库存台账（联表带出物料/仓库名称） |
| GET | `/api/inv/order/list` | `inv:order:list` | 出入库单列表，`orderType` 传 `IN`/`OUT` 区分 |
| GET | `/api/inv/order/{id}` | `inv:order:query` | 单据详情（**含明细**） |
| POST | `/api/inv/order` | `inv:order:add` | 新增单据（含明细），状态为草稿 |
| PUT | `/api/inv/order` | `inv:order:edit` | 修改（**只有草稿可改**） |
| DELETE | `/api/inv/order/{ids}` | `inv:order:remove` | 删除（**只有草稿可删**） |
| POST | `/api/inv/order/audit/{id}` | `inv:order:audit` | **审核 → 写库存台账 + 写流水** |
| POST | `/api/inv/order/cancel/{id}` | `inv:order:audit` | 作废（**已审核的单据不允许作废**，见下） |
| GET | `/api/inv/log/list` | `inv:log:list` | 库存流水 |

**审核的并发安全要求**（这是库存模块唯一真正难的地方）：
出库时必须用 `UPDATE inv_stock SET qty = qty - #{qty} WHERE warehouse_id=? AND material_id=? AND qty >= #{qty}`
这种**带条件的原子更新**，根据影响行数判断是否成功；影响 0 行即库存不足，抛业务异常回滚。
绝不能"先 select 查库存、再判断、再 update" —— 并发下两个请求都能查到够，然后一起扣成负数。

### 4.5 采购管理 `/api/pur`

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/pur/order/list` | `pur:order:list` | 采购订单列表 |
| GET | `/api/pur/order/{id}` | `pur:order:query` | 订单详情（含明细） |
| POST | `/api/pur/order` | `pur:order:add` | 新增订单（含明细），总金额由明细汇总，**不接受前端传入** |
| PUT | `/api/pur/order` | `pur:order:edit` | 修改（只有草稿可改） |
| DELETE | `/api/pur/order/{ids}` | `pur:order:remove` | 删除（只有草稿可删） |
| POST | `/api/pur/order/audit/{id}` | `pur:order:audit` | 审核订单 |
| POST | `/api/pur/order/cancel/{id}` | `pur:order:audit` | 作废 |
| GET | `/api/pur/receipt/list` | `pur:receipt:list` | 收货单列表 |
| GET | `/api/pur/receipt/{id}` | `pur:receipt:query` | 收货单详情 |
| GET | `/api/pur/receipt/pendingOrders` | 需登录 | 已审核且未收完的订单（+ 明细），做收货时选单用 |
| POST | `/api/pur/receipt` | `pur:receipt:add` | 新增收货单（草稿） |
| DELETE | `/api/pur/receipt/{ids}` | `pur:receipt:remove` | 删除（只有草稿可删） |
| POST | `/api/pur/receipt/confirm/{id}` | `pur:receipt:confirm` | **确认收货 → 生成入库单 → 增加库存 → 写流水** |

## 五、后端分层规范

```
controller/   只做参数校验 + 调用 Service + 包 R。禁止写业务逻辑、禁止注入 Mapper
service/      接口 IXxxService
service/impl/ 实现，写操作加 @Transactional(rollbackFor = Exception.class)
mapper/       继承 BaseMapper，类上标 @Mapper
domain/       实体，继承 BaseEntity，标 @TableName
domain/dto/   入参，带 jakarta.validation 注解；查询条件继承 PageQuery
domain/vo/    出参
resources/mapper/{模块}/XxxMapper.xml   只写复杂联表
```

### 硬性规则

1. **手写 XML 必须自己带 `is_deleted = 0`**。MyBatis-Plus 的逻辑删除只对 `BaseMapper` 自动生成的方法生效。
2. **分页 XML 的 `IPage` 必须是第一个参数**，否则分页静默失效（不报错，只是查出全表）。
3. **跨模块调用只能注入对方模块暴露的接口**，禁止直接访问别的模块的 Mapper 或表。
   库存要物料信息，就注入 `com.erp.mdm.api.MdmApi`，不要注入 `MdmMaterialMapper`。
   这条规则是将来拆微服务时唯一需要改的地方。
4. **金额、数量用 `BigDecimal`**，禁止 `double`/`float`。
5. **金额计算放在 Service**，禁止前端传总金额（`total_amount`、`amount` 一律后端算）。
6. **单据状态流转必须用带条件的原子 UPDATE，并放在动数据之前**。详见下一节。

## 五之二、单据状态流转：并发下唯一正确的写法

这是全工程最容易写错、且错了以后最难复现的一处。

### 错误写法（看起来完全合理）

```java
InvOrder order = orderMapper.selectById(id);
if (!STATUS_DRAFT.equals(order.getStatus())) {        // ← 检查
    throw new ServiceException("单据已审核");
}
for (明细 : 明细列表) {
    库存 += 明细.数量;                                 // ← 副作用
}
orderMapper.updateById(带 status=AUDITED 的实体);       // ← 改状态
```

**问题**：`selectById` 与 `updateById` 之间没有任何互斥。两个并发请求
（用户双击、或两个人同时点）会双双读到「草稿」、双双通过检查、**库存被加两次**，
而且两个请求都返回成功，事后完全看不出是哪一次重复了。

### 正确写法

```java
// 1) 先抢占状态：把「检查」和「改」合并成一条 SQL，由数据库行锁互斥
int rows = orderMapper.update(update, new LambdaUpdateWrapper<InvOrder>()
        .eq(InvOrder::getId, id)
        .eq(InvOrder::getStatus, STATUS_DRAFT));   // ← 关键条件
if (rows == 0) {
    throw new ServiceException("单据状态已变更，请刷新后重试");   // 有人抢先了
}

// 2) 抢到之后再做副作用。这一步失败会整体回滚，状态自然退回草稿
for (明细 : 明细列表) { 库存 += 明细.数量; }
```

### 三条要点

1. **顺序必须是「先改状态，后动数据」**。反过来（先动库存再改状态）的话，
   第二个请求的库存变动已经发生了，这时候再抛异常也来不及回滚别人的变更。
2. **判断依据是影响行数**，不是 `updateById` 的返回值（后者不告诉你条件是否命中）。
3. **行锁 + 同一事务**就能保证正确性，不需要额外引入分布式锁 ——
   这是单体架构白拿的收益之一。拆成微服务后，这里就必须换成分布式锁或幂等号。

同样的模式已用在：`InvOrderServiceImpl.transitStatus`（审核/作废）、
`PurReceiptServiceImpl.confirm`（收货确认）、`PurOrderServiceImpl.audit/cancel`。

> 库存台账的增减本身也是同一种思路：出库用
> `UPDATE ... WHERE qty >= #{qty}` 并按影响行数判断，把「够不够扣」交给数据库在行锁内裁决。

## 六、新增一个 CRUD 模块的 SOP

以「新增一个和物料一样的模块」为例，照抄 `erp-mdm` 的 `material` 相关文件改名字即可。

### 需要新建的文件（以 erp-mdm 的供应商为例，11 个）

```
1.  domain/MdmSupplier.java                              实体，继承 BaseEntity
2.  domain/dto/MdmSupplierQuery.java                      继承 PageQuery
3.  mapper/MdmSupplierMapper.java                         @Mapper extends BaseMapper
4.  resources/mapper/mdm/MdmSupplierMapper.xml            只在需要联表时写
5.  service/IMdmSupplierService.java
6.  service/impl/MdmSupplierServiceImpl.java              编码唯一校验 + CRUD
7.  controller/MdmSupplierController.java                 6 个端点 + @PreAuthorize
    （若被其他模块需要，再加 api/MdmSupplierApi + api/impl/...）
```

### 需要修改的文件

```
8.  erp-admin/src/main/resources/db/migration/V2__schema_mdm.sql        加建表（已存在则新增 V2_1__xxx.sql）
9.  .../db/migration/R__seed_system_menu.sql                            加菜单 + 按钮权限行
10. erp-web/src/api/mdm/supplier.js                                     前端接口文件
11. erp-web/src/views/mdm/supplier/index.vue                            前端页面（照抄 material/index.vue）
```

### 验收清单

- [ ] `mvn -pl erp-modules/erp-mdm -am install -DskipTests` 通过

- [ ] 列表分页正常，`total` 与数据库行数一致

- [ ] 用无权限的账号登录，新增按钮不显示，直接调接口返回 403

## 七、前端规范

1. **接口统一写在 `src/api/{模块}/{资源}.js`**，组件里禁止直接 `import axios`。
2. **按钮权限用指令 `v-hasPermi="['mdm:material:add']"`**，不要用 `v-if` 手写判断。
3. **字典下拉统一用 `<DictSelect v-model="x" type="mdm_unit" />`**，不要每个页面手写 options。
4. **表格里的状态列用 `<DictTag :value="row.status" type="sys_normal_disable" />`**，颜色来自字典的 `listClass`。
5. **页面文件统一 `index.vue`**，放在以资源命名的目录下，与后端 `component` 字段对应
   （菜单表里写 `mdm/material/index`，前端就放在 `views/mdm/material/index.vue`）。
