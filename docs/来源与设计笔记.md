## 一、设计是怎么定下来的

原始设计文档（`docs/archive/原始设计文档.md`）描述的是一套
「8 微服务 + Docker Compose + Nacos + 每服务一个库」的架构。
落地前先对**本机实际环境**做了一轮实测，结论是那套方案一步都跑不通。

### 实测记录（原始命令与结果）

```bash
$ java -version
java version "21.0.12" LTS                     # 装了 21
$ mvn -v
Java version: 1.8.0_202, runtime: D:\Program Files\Java\jdk1.8.0_202
                                               # 但 Maven 跑在 JDK 8 上（读的是 JAVA_HOME）
$ docker -v
bash: docker: command not found                # 没有 Docker
$ node -v
v20.11.1
$ netstat -ano | grep LISTENING
TCP  0.0.0.0:3306  LISTENING                   # MySQL80 在跑
TCP  0.0.0.0:1433  LISTENING                   # SQL Server 在跑（金蝶账套库）
                                               # 6379(Redis) 与 8848(Nacos) 都没有监听
```

### 由此推导出的四个决定

| 决定 | 依据 |
|---|---|
| 改用**模块化单体**，不拆微服务 | 没有 Docker/Nacos 起注册中心；8 个进程的本地开发成本远超收益 |
| **不引入 Redis**，用 Caffeine | 6379 无监听；单体单进程部署本来也不需要分布式缓存 |
| **不引入 Nacos/网关/Feign** | 8848 无监听；单体下一个进程一个端口，不需要服务发现 |
| 数据库用**本机 MySQL 8** | 3306 已在跑，不需要 Docker 装第二个 MySQL |

### 版本上的硬约束（不是"选新的好"，是环境反推的）

1. **Vite 只能用 6.x**。npm 实测 `vite@7` 与 `vite@8` 的 `engines` 是
   `^20.19.0 || >=22.12.0`，本机 Node 20.11.1 不满足；
   而 `vue-router@5` 又要求 Vite `^7 || ^8`，所以 vue-router 也只能锁 4.x。
2. **`@vitejs/plugin-vue@6` 需要 Node 20.12+**（内部用了 `crypto.hash()`）。
   本机 20.11.1 会在 build 时报 `crypto.hash is not a function`。
   已在 `vite.config.js` 加了兼容补丁；**根治办法是升 Node 到 20.12+/22 LTS 后删掉补丁**。
3. **Spring Boot 用 3.5.x 不用 4.x**。周边生态跟进有限，MVP 阶段不值得冒运行异常的风险。

### 版本全部经实测确认存在

`Spring Boot 3.5.16`、`mybatis-plus-spring-boot3-starter 3.5.17`、`jjwt 0.12.7`、
`hutool 5.8.48`、`springdoc 2.8.17`、`mysql-connector-j 9.7.0`
—— 都通过请求 Maven Central 的 `maven-metadata.xml` 确认过，不是凭记忆写的。
（曾选的 `knife4j 4.5.0` 后来被移除，理由见第四节。）

## 三、代码评审记录

### 已修正的问题

按发现顺序排列。**带「实测发现」标记的，是只有真正跑起来才暴露、静态检查发现不了的错误。**

| # | 问题 | 现象 | 修正 |
|---|---|---|---|
| 1 | 自建 logback 用 `%clr` 却没 include Spring Boot 的 defaults | **应用完全无法启动**，报 `no conversion class registered for [clr]` | 加 `<include resource=".../logback/defaults.xml"/>` |
| 2 | `type-aliases-package` 引发类别名冲突 | **应用无法启动**，报 `The alias 'TreeSelectVo' is already mapped to ...` | `TreeSelectVo` 下沉到 `erp-common`，删两份重复；移除 `type-aliases-package` |
| 3 | knife4j 与 Spring Boot 3.5 不兼容 | 接口文档打不开，`/v3/api-docs/*` 报 `NoSuchMethodError: SpringDocConfigProperties.getGroupConfigs()` | 弃用 knife4j，改用 springdoc 原生 Swagger UI |
| 4 | 前后端字段名不一致 | `bizDateStart` vs `bizDateBegin` → 日期筛选**静默失效**；`materialCode` 后端无此字段 → 筛选被忽略。**接口返回 200、页面正常，只是数据不对** | 统一命名；后端补 `materialCode` 筛选（经 `MdmApi` 解析编码→ID，不破坏模块边界） |
| 5 | 菜单管理缺少 Controller | 菜单表里有 `system:menu:*` 权限按钮但没有对应接口 | 补 `SysMenuController` |
| 6 | 超级管理员用「用户 ID == 1」判断 | 主键自增，重建库/导数据后 admin 就不是 1 号；判断失效的症状是「管理员突然没权限了」，极难联想 | 改为按用户名 `admin` 与角色 `admin` 判断 |
| 7 | `updateUser` 时 `roleIds` 为 null 会清空角色 | 任何漏传 roleIds 的调用都静默清空用户角色 | 区分语义：`null` = 不改角色，`[]` = 明确清空 |
| 8 | 删菜单不清角色授权 | `sys_role_menu` 留下指向已删菜单的行；ID 被复用后相关角色会凭空多出权限 | 删菜单前先清授权 |
| 9 | `TreeUtils.build` 早期实现 | 边遍历边挂子节点，每个节点只保留最后一个子节点 | 改为「建索引 → 归组 → 统一赋值」三趟遍历 |
| 10 | 响应体里多出 `success` 字段 | Lombok 生成的 `isSuccess()` 被序列化，与契约（只有 code/msg/data）不符 | 加 `@JsonIgnore` |
| 11 | 单据状态流转不是原子的 | 审核/确认是「先 select 查状态 → 判断 → 改状态」，两个并发请求都通过检查：库存单被加两次、收货单生成两张入库单。**两个请求都返回成功，事后看不出哪次重复** | 改为带条件的原子 UPDATE（`WHERE status = 期望值`）并按影响行数判断，且放在动数据**之前**。已修 5 处 |
| 12 | **实测发现**：登录查用户时 SQL 漏了 `password` 列 | 账号密码都对却总提示「用户名或密码错误」，**日志里没有任何异常**（只是正常的认证失败）。SQL 少一个列名，编译器完全没有意见 | `selectUserByUsername` 补上 `u.password`（仅此一处，安全性由 `@JsonProperty(WRITE_ONLY)` 保证） |
| 13 | **实测发现**：`@PreAuthorize` 拒绝时返回 HTTP 200 | 契约规定 403 要用真实状态码（前端据此区分「登录过期」与「无权限」），但实现返回的是 HTTP 200 + body.code=403 | 异常处理器改用 `ResponseEntity` 返回 HTTP 403，与 Security 的 `AccessDeniedHandler` 一致 |
| 14 | **实测发现**：`ResultCode` 里 `BUSINESS_ERROR` 与 `ERROR` 都是 500 | 排障时分不清「用户操作不合法」和「我们的代码出错了」，实测中因此多绕一圈 | `BUSINESS_ERROR` 改为 400；**body.code=500 从此必定意味着程序有 bug** |
| 15 | **浏览器实操发现**：侧边栏 `<el-menu>` 漏了 `router` 属性 | 点击菜单项**不跳转**，只是高亮一下、页面内容不变。ELement Plus 的 `el-menu` 默认不做路由导航 | 加 `router` 属性。`el-menu-item` 的 `index` 本来就是完整路径（`/system/user`），加上即可 |
| 16 | **实测发现**：在 `<style scoped>` 里用了 `//` 注释 | 构建直接失败，报 `[vite:vue] Unexpected '/'`。Vue 单文件组件的 `<style>` 默认是**普通 CSS**（不是 SCSS），`//` 在 CSS 里非法 | 改成 `/* */`；或给 `<style>` 加 `lang="scss"`。本项目样式块统一用普通 CSS + `/* */` |
| 17 | **实测发现**：只改侧栏容器宽度为 50px，折叠后图标被裁 | Element 的折叠宽度是 `--el-menu-icon-width + 2 × --el-menu-base-level-padding`（默认 24+40=64），容器再窄也没用 | 同时覆盖这两个令牌为 24+13×2=50，并把折叠态菜单的横向内边距去掉 |
| 18 | **实测发现**：`el-menu` 上残留深色配色 props | `background-color` / `text-color` / `active-text-color` 会被 Element 写成 CSS 变量注入，直接压过 `sidebar.scss`，表现为「样式改了但侧栏还是深色」 | 删除这三个 props，配色只在 `sidebar.scss` 一处维护 |
| 19 | **实测发现**：菜单只授权子项、不授权父目录 | 把仓库管理(204)移到库存管理(3)下后，采购员角色看不到仓库菜单：`TreeUtils` 拼树时找不到父节点就**静默丢弃**子项，日志无任何异常 | 角色授权里同时授予父目录 3；E2E 增加「采购员在库存管理下只看到仓库管理」断言，把这条规则钉住 |
| 20 | **实测发现**：在 `erp-admin` 子模块跑 `mvn spring-boot:run` 不重编译兄弟模块 | 给 `RouterVo` 加了 `groupName` 并重启后端，接口下发里却没有这个字段；日志无异常 —— 因为运行的仍是本地仓库里旧的 `erp-system` jar | 要么先在 `erp-server` 根目录 `mvn clean install -DskipTests` 再启动，要么用 `mvn -pl erp-admin -am spring-boot:run`。已写进 README / CLAUDE |
| 21 | **实测发现**：功能导航页拼出的链接少了上级目录 | 从「采购管理」工作台点「采购订单」返回 **404**：二级目录的 `path` 是相对值（`purchase`），页面直接把它当根路径，拼出 `/purchase/order`，正确值应是 `/supply/purchase/order`。顶级模块的 path 是绝对值（`/supply`），所以没暴露 | `findRouteByPath` 查找时同时返回 `fullPath`，页面用它作为子功能的基准路径 |

> 第 15 条值得单独说一句：前面 49 项端到端断言全部通过，**唯独没抓到它**——
> 因为那些断言测的是 HTTP 接口，而这是纯前端的交互问题。
> 这正是把「浏览器端交互与渲染」明确列为"未验证"的原因：接口全通 ≠ 页面能用。
> 对应的教训是，验证清单里"未验证"那几项不是敷衍的免责声明，而是真的有可能藏着 bug。

### 有意为之、不是 bug 的取舍

| 取舍 | 理由 |
|---|---|
| 业务失败返回 HTTP 200 + `body.code=400` | HTTP 层请求成功送达并处理了，失败在业务语义层。但 401/403 用真实状态码，因为前端要区分「登录过期」与「无权限」。**代价**：只看 HTTP 状态码会把失败当成功（实测中就把坏掉的接口文档误判为正常），所以验收必须看响应体里的 `code` |
| `Long` 序列化成字符串 | 防 JS 精度丢失。只转包装类型，`long total` 仍是数字 |
| 登录态缓存在进程内 Caffeine | 单体单进程足够；重启应用导致重新登录，开发阶段可接受。换 Redis 只需改 `TokenService` 一个类 |
| JWT 里只放 tokenId，不放权限 | 权限变更能立刻生效；Token 不会因为权限多而超长；支持登出/踢人 |
| 超级管理员用通配符 `*:*:*` 而非展开权限点 | 展开的话每次登录要扫全表，且新增菜单后旧 Token 里没有新权限，表现为「给管理员加了菜单却点不动」 |
| `sys_user_role` / `sys_role_menu` 不做逻辑删除 | 取消授权就是删一行，留历史没意义 |
| 不引入 MapStruct | 字段命名高度一致，用 MapStruct 要额外处理它与 Lombok 的注解处理器顺序，骨架阶段性价比不高 |
| 管理员密码由 Java 启动时创建而非写进 SQL | BCrypt 每次盐不同，哈希没法肉眼校验；抄错的现象是「密码对却登录失败」 |
| 库存流水 `qty`：入库为正、出库为负 | 与建表脚本注释一致；另有 `biz_type` 可判断方向，冗余是刻意的（报表直接 SUM 就得净变动） |
| 单据采用「列表 → 卡片页」而非弹窗 | 单据能被 URL 直接打开、刷新不丢；明细表有足够横向空间；列表「浏览」与卡片「处理」两种心智不互相打断。**代价**：新增接口只返回 `R<Void>`，前端拿不到新单号，所以保存后回列表而不是停留在卡片 |
| 采购收货草稿不可编辑 | 后端只提供新增 / 确认 / 删除，没有修改接口。要支持需补 update（并重算明细与订单未收数量），所以卡片页里已存在的收货单只读 |

## 四、本地环境上踩的坑（与业务无关，但会挡住启动）

### 1. `JAVA_HOME` 指向 JDK 8

Maven 读 `JAVA_HOME` 而不是 `PATH`，不改成 JDK 21 会报 `invalid target release: 21`。
顺带收益：JDK 8 下 Maven 的 `platform encoding` 是 GBK，中文注释容易乱码。

### 2. `~/.m2/settings.xml` 的本地仓库指向不存在的目录

`settings.xml` 里的 `<localRepository>` 指向了一个不存在的自定义目录，
Maven 会新建并全量下载。不影响使用，但若想改回默认位置，把那一行注释掉即可。
（另外文件里有三个镜像，实际生效的是 `mirrorOf=central` 的那个，已改为可达的 https 地址。）

### 3. MySQL root 密码遗忘后的重置

见 `tools/reset-mysql-root-password.md`。那里面记了三个真实的坑：
直接运行 mysqld 需要用 `--defaults-file` 指定配置（否则数据目录找不到）、
强制结束 mysqld 后要等句柄释放才能启动服务、以及 `.bat` 装中文会导致注释行被当命令执行。
